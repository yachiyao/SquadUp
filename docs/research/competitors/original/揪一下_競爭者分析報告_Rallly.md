## 3. 官方網站內容與功能分析

### 3.1 主要操作流程

1. **建立投票：** 主辦人設定活動名稱、候選日期及時間。
2. **分享連結：** 透過通訊軟體或電子郵件邀請其他人參與，不強制參與者註冊。
3. **參與者投票：** 選擇可以、不可以、勉強可以參加的時間，檢視投票狀況。
4. **確認最終時間：** 主辦人選定時間，並利用相關通知或行事曆功能告知參與者。

### 3.2 核心功能

| 功能 | Rallly 提供的內容 |
|---|---|
| 活動建立 | 設定標題、候選日期與時間；地點欄位及設定方式依版本確認 |
| 訪客參與 | 參與者可不註冊，使用基本投票功能 |
| 多人投票 | 支援 Yes、No、If Need Be 三種回應 |
| 投票統計 | 以表格呈現每位參與者的可出席時間 |
| 留言討論 | 在投票頁面討論活動細節 |
| 時區轉換 | 支援跨時區時間顯示 |
| 最終確認 | 主辦人選定時間並通知參與者 |
| 會員管理 | 管理歷史投票及通知 |
| 行動裝置 | 支援手機瀏覽與投票 |
| 開源部署 | 可自行部署於伺服器 |

### 3.3 介面設計觀察

- **低學習成本：** 參與者不需先建立完整會員資料。
- **資訊集中：** 候選時間、投票人員與結果集中展示。
- **快速完成任務：** 以建立活動、分享連結、投票為主要操作。
- **三態投票：** 「可以／勉強可以／不可以」比純二元投票更能表達真實出席彈性。

| 面向 | 分析 |

| **W — 劣勢** | 核心偏重時間投票，地點協調並非主要功能；免費版歷史資料保留與進階功能可能受限。 |

### 4.2 值得「揪一下」參考的設計

1. **訪客優先：** 使用者設定暱稱即可投票，降低進入門檻。
2. **清楚呈現支持程度：** 除投票人數外，可呈現尚未回覆人數與「勉強可以」的人數。
3. **時間與地點的雙重協調：** 在同一活動中分別投票時間和地點，形成產品差異化。
4. **活動結果即時更新：** 主辦人定案後，參與者利用原連結查看最新結果，不必重新分享網址。

## 5. 分析總結與產品建議

Rallly 已將多人時間投票、訪客參與、結果統計及最終確認等基本功能做得相當完整，因此「揪一下」不宜單純以**免費時間投票**作為唯一賣點。

更適合的產品定位是：

> **「揪一下」不只是找出大家有空的時間，而是協助朋友、社團與小型群組，從時間、地點到最終決策，一次完成聚會協調。**

建議優先開發以下 MVP（最小可行產品）能力：

1. 時間投票。
2. 地點投票（允許多候選地點）。
3. 訪客暱稱參與。
4. 最終結果即時同步、原連結查看。

中期再評估會員歷史紀錄、Email 通知、提醒未回覆者、外部行事曆整合等功能。產品重點應放在**「協助聚會完成決策」**，而非僅「找出共同空閒時間」。
